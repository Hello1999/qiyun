# 项目定义 · 栖云 Qiyun

版本：方案草案 0.1；日期：2026-10-04。首批管理对象已由用户确认：Linux 云服务器 / VPS，主要运行 Docker 和网站。

## 1. 项目是什么

一个可自托管的 AI 运维工作台。它拥有服务器的真实状态、受限制的操作能力和完整任务记录，让用户用一句话完成从理解现状到执行验证的流程。

产品的三个核心承诺：

1. **看得懂：** 把资源、服务状态和日志解释成可采取行动的信息，并给出证据。
2. **做得稳：** 每次操作指向确定的主机与服务，由代码校验权限和参数，执行后检查结果。
3. **查得到：** 能回答谁在何时修改了什么、为什么、结果如何、是否具备恢复条件。

## 2. 为谁解决什么问题

第一批用户是独立开发者、小型 SaaS 团队和管理约 1–10 台 VPS 的技术人员。这个数量是产品设计目标，不是已验证容量。

典型场景：网站突然打不开、容器反复重启、磁盘接近满、证书将到期、需要升级服务，却要在多个终端、日志和配置文件之间来回切换。工作台聚合这些信息，Agent 负责跨工具调查，用户保留对服务变更的掌握。

首版先验证单机完整闭环，再扩展多机。架构从第一天保留主机标识和资源作用域。

## 3. 产品能做什么

| 能力 | 首版计划 | 后续扩展 |
| --- | --- | --- |
| 服务器总览 | CPU、内存、磁盘、负载、采集时间、连接状态 | 多机分组、容量趋势、资源预算 |
| 服务总览 | Docker/Compose、已登记 systemd 单元、健康状态、端口 | 更多适配器、依赖关系图 |
| 网站检查 | 已登记站点的 HTTP、TLS 到期、基础可达性 | 多地域探测、合成检查、SLO |
| 故障调查 | 有界日志、容器事件、资源状态交叉分析，附来源 | 故障案例库、跨主机关联 |
| 运维操作 | 确认后重启指定容器/服务 | 有范围的预授权流程 |
| 配置与更新 | 受管 Compose 字段变更、固定镜像版本更新、健康检查 | 应用模板、分批发布 |
| 版本与恢复 | 差异、历史记录、满足条件时恢复配置/镜像 | GitOps 对接、环境晋级 |
| 语音 | 按住或点击说话 → 可编辑转写 → 提交任务 | 可选播报、长对话 |
| 自动化 | 首版监测规则和手动调查；MVP+增加定时巡检 | 窄范围自动修复、告警联动 |

“各种服务”采用逐步增加适配器的方式实现。无法识别的进程可显示基础信息，但不承诺自动理解其运维语义。

## 4. 用户可以怎样说

| 自然语言 | 实际行为与完成标准 |
| --- | --- |
| 看看这台机器有哪些服务不健康 | 返回采集时间、异常目标和具体状态；离线不显示为正常 |
| 网站打不开，帮我查原因 | 读取站点探测、容器、端口与日志；区分事实和可能原因 |
| 最近半小时 CPU 为什么这么高 | 使用已有采样分析；没有历史数据时明确说不足 |
| 整理博客服务最近的报错 | 只读取允许范围和数量的日志，脱敏后解释并链接证据 |
| 重启博客服务 | 展示目标和中断影响，确认后执行并检查健康 |
| 把这个服务内存限制改成 1 GB | 验证受管字段，展示差异和资源影响，确认后应用 |
| 把网站更新到这个镜像版本 | 固定 digest，检查现有配置和恢复条件，确认后更新 |
| 恢复昨天的配置 | 选择具体 Git 版本，检查当前漂移，生成新的恢复计划 |

所有产品示例都需要真实工具支撑；设计原型可使用明确标记的演示数据。

## 5. 自动化边界

| 操作类别 | 默认行为 |
| --- | --- |
| 已授权范围内的查询、诊断 | 自动执行，带读取范围、时间和输出量限制 |
| 服务重启、受管配置修改、指定镜像更新 | 先形成具体计划，确认后执行 |
| 未来的自动修复 | 用户先配置服务、动作、条件、次数、时间窗和熔断规则 |
| 删除数据卷、数据库迁移、SSH/防火墙/权限修改 | 首版不提供自动执行能力 |
| 任意 Shell、任意路径写入 | 首版不开放 |

确认必须绑定实际操作与参数；日志、网页内容、模型输出不能自我授权。停用自动化和停止新任务的入口应始终可达。停止请求不等于正在进行的操作已撤销。

## 6. 首版范围与非目标

支持基线暂定 Ubuntu 24.04 LTS，先验证 amd64，正式 MVP 同时覆盖 arm64。Debian 等发行版后续经过安装、权限和工具验证再纳入支持矩阵。

首版为单管理员、自托管、单实例控制端、单台主机闭环；小规模多机放在下一阶段。不同时建设 Kubernetes 平台、企业 SSO、复杂 RBAC、多租户托管 SaaS、在线终端、数据库管理平台或完整备份系统。

语音是首版目标，但排在真实执行闭环之后；浏览器不支持或 ASR 不可用时始终保留文字输入。语音转写服务和模型推理服务分开配置。

## 7. 如何推进与验收

以下为门槛驱动的里程碑，不作为固定工期承诺。

| 阶段 | 交付内容 | 完成门槛 |
| --- | --- | --- |
| P0 定义（本轮） | 产品、架构、设计、接入说明、AGENTS.md、Git 初始提交 | 范围与风险明确；区分规划和已实现；无凭据入库 |
| P1 体验与只读闭环 | 核心页面、登录、配对、主机 Agent、状态/日志/站点检查 | 在测试 Linux 主机运行；真实状态一致；离线与权限不足可理解 |
| P2 受控动作 | 一次容器/服务重启全过程 | 未审批不执行；审批后参数变更被拒绝；重连不盲目重做；健康验证有结果 |
| P3 可用 MVP | 受限 Compose 配置和镜像更新、Git历史、语音、安装与升级 | 能完整复现下面的演示任务；安装、升级和恢复经过验证 |
| P4 小范围试用 | 1–10 台服务器、巡检规则、成本/任务统计 | 收集真实使用数据，再决定团队功能与自动修复范围 |

MVP 演示任务：安装 → 接入服务器 → 查看网站 → 文字或语音发现测试故障 → 展示修复方案 → 确认重启 → 验证恢复 → 查看变更记录。另用一次受管配置更新展示差异与恢复。

## 8. 衡量目标

- 安装：支持矩阵内的干净测试机能够重复安装；失败时指出具体原因，保留原服务与数据。
- 可靠性：每种写工具都通过未批准、参数漂移、重复投递、执行中断线、回执丢失的测试。
- 真实性：成功只由工具结果和后置检查决定；模型文字不能把失败任务标记成功。
- 体验：主要状态和动作在核心页面可见；键盘、窄屏、降低动画偏好均可用。
- 产品效果：记录首次任务完成率、人工介入原因、故障处理时间、每个成功任务的调用/token用量。套餐额度以可观测数据为准，费用分摊标注估算，不把 token 数伪装成真实账单。
- 内部性能预算：在声明的测试条件下追求首屏可交互 ≤ 2 秒、交互反馈 ≤ 100 毫秒、常规状态新鲜度 ≤ 15 秒。模型响应与真实服务重启时间单独统计；这些是待验证预算。

## 9. 前景与长期目标

近期目标是成为开发者每天愿意打开的服务器工作台。中期形成经过验证的运维流程库，让巡检、更新和恢复可复用。长期拓展团队协作、多机变更与策略控制，让自动化逐步承担可明确授权的重复工作。

可持续优势来自对真实环境的理解、稳定的执行与恢复、适配器质量、任务证据和顺畅体验。模型和视觉效果是重要组成，但不能单独形成长期优势。

商业化作为待验证假设：基础单机自托管能力，增值方向包括多机/团队、审批策略、企业集成和技术支持。是否开源、采用何种许可证、如何定价，需要后续决定；现在不加入商业限制，也不假定有市场规模或付费转化数据。

主要不确定性包括模型使用成本、不同环境的兼容性、用户愿意交给系统的操作范围，以及持续使用频率。用早期真实任务数据决定扩展方向。

## 10. 已决定与待核实

已决定：Linux/VPS 优先、Docker/网站优先、自托管、Web + 语音方向、Ark + DeepSeek、Git 管理、年轻舒适的设计。

工程暂定：React/TypeScript 控制端、Go 主机 Agent、SQLite 单实例、Ubuntu 24.04 基线。

用户补充决定：产品运行时按指定 Coding Plan 端点接入，不把套餐适用范围作为工程推进前置条件，也不自动改为按量付费接口。

实施前需核实：模型实测能力与限流、ASR 供应方与费用、真实测试机、远程仓库归属、发行域名、名称与许可证。以上不阻塞本轮定义和不连接真实主机的界面开发。
