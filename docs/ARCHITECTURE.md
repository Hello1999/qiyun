# 技术架构

更新日期：2026-10-04。本文区分首版已有实现与后续设计约束。工作台、控制端、主机 Agent 和独立 helper 已存在；配置部署、网站主动探测、证书轮换与签名发行尚未实现。运行入口见 [RUNNING.md](RUNNING.md)。

## 1. 当前分层

| 层 | 当前技术 | 当前职责 |
| --- | --- | --- |
| Web | React + TypeScript + Vite、Motion、Lucide、原生 CSS | 资源视图、文字 / 浏览器语音入口、方案确认、任务时间线 |
| 控制端 | Node.js + TypeScript + Fastify | 身份、资产、策略、Ark 编排、任务 API、审计记录 |
| 数据 | Node.js SQLite、WAL | 单实例设置、会话、快照、任务、作业与配对状态 |
| 主机 Agent | Go 标准库、独立可执行文件 | 采集、HTTPS 配对、mTLS 轮询、持久作业与结果回传 |
| 特权 helper | 同一 Go 程序的独立运行模式、Unix socket | 白名单 Docker / systemd 读取与重启、签名校验、执行收据 |
| 模型 | Ark Chat Completions 适配器 | 流式消息解析、受限只读工具与重启建议、预算与错误处理 |
| 语音 | 浏览器 SpeechRecognition | 可编辑转写；不支持时保留文字输入 |
| 部署 | Docker / Compose 源码构建、systemd 模板 | 启动控制端，辅助管理员部署 Agent / helper |

依赖版本与锁文件已入库维护，不使用浏览器端模型密钥。没有引入分布式工作流平台、消息中间件或多个数据库，也没有独立的 `packages/ui` 空包。

数据路径：浏览器 → 控制端 → 模型与策略 → 持久任务 → 主机 Agent → helper → Docker / systemd。模型只提出结构化建议，不能自行授权写操作。

## 2. 连接与身份

浏览器与主机通道分离：Web / API 默认 `127.0.0.1:4310`，主机 HTTPS 通道默认 `127.0.0.1:4311`；开发 Web 为 5173，端口可通过环境配置调整。控制端容器不挂 Docker socket。

浏览器使用 HttpOnly、SameSite 会话 Cookie，HTTPS 来源下设置 Secure；修改请求校验明确的 Origin 和 CSRF。首位管理员初始化受本机访问限制，远程场景使用可信的本地端口转发或运行文档中的交互初始化工具。当前为单管理员，不提供团队权限界面。

Agent 以普通专用用户运行，主动采集并通过 HTTPS 轮询领取任务、回传结果，不开放公网管理端口。一次性配对令牌短期有效；初始 CA 必须通过可信渠道交付。注册使用本地生成的私钥和 CSR，后续通道要求 mTLS，证书绑定主机身份。

现有客户端证书有效期为 90 天，续期、轮换、吊销和对应 Web 管理流程尚未实现。修改域名配置不会自动重签已有证书，不得以删除 CA 作为无损修复方式。

## 3. 主机权限边界

无 helper 时，Agent 读取主机指标及普通用户权限允许的已登记 systemd 信息，不获得 Docker 访问或重启能力。

启用 helper 后，由 root 控制其二进制、配置、签名公钥、状态目录和父目录。helper 通过 Unix `SO_PEERCRED` 与 socket 权限确认调用方 UID，并验证签名任务、主机、服务、动作、有效期、本地白名单和期望 revision。

Docker 读取与重启分别授权；自动发现被标记的容器不会自动获得重启权限。systemd 同样区分读取列表和重启白名单。Docker 重启使用已检查的不可变容器 ID；systemd 使用固定程序路径与独立 argv，不拼接 Shell。

Docker socket 具有宿主高权限，仅 helper 接触它。该设计限制 Agent 的能力，并不将 helper 或控制端签名权限被完全攻陷的情况描述为可抵御；mTLS 只证明身份，不代替授权。

## 4. 当前工具与任务

模型工具为 `read_inventory`、`read_service_logs`、`propose_service_restart`。最后一个工具只形成建议；实际写动作固定为 `service.restart`。手动重启也进入相同策略与审批路径。

当前流程：

1. 用户提交请求及可选主机 / 服务范围。
2. 读取该范围内快照与有界日志；模型输出和日志均不提升为指令权限。
3. 查询任务输出结论；重启建议由控制端校验目标、白名单与资源状态。
4. 返回计划，展示影响、执行后验证与恢复能力；批准绑定计划 hash。
5. 控制端核对期限与 revision，再签发固定目标、动作、版本和到期时间的任务。
6. Agent 与 helper 再次校验，执行并保存收据。
7. 核对容器运行 / 声明的健康状态或 systemd active 状态，持久化结果。

当前核对不包含主动 HTTP / TLS 或业务请求检查。服务 CPU / 内存采集尚未实现时返回 null；主机指标为真实采集，CPU 首次采样不足同样返回 null。

网页通过 API 刷新资源与任务，不向用户展示模型内部推理文本。语音文本可修改后提交，写操作仍走同一链路。浏览器识别服务可能处理音频，产品未实现独立 ASR，也不在控制端存储录音。

## 5. 状态、并发与未知结果

契约包含 `observing`、`awaiting_approval`、`queued`、`running`、`verifying`、`succeeded`，以及 `failed`、`cancelled`、`unknown`、`expired` 分支；具体任务可跳过不适用阶段。成功由工具结果与状态核对决定。

- 控制端限制同一数据库的服务实例，并通过资源唯一约束阻止同一服务的活动写作业冲突；这不是分布式租约或 fencing 实现。
- helper 串行执行写操作，对状态目录持有进程锁。副作用前持久化 running 收据，结果写入后续收据；重复任务返回既有结果，不重复执行。
- helper 崩溃留下的未完成收据、超时或丢失响应可能变为 unknown，不能将其当作可安全重试的失败。
- Agent 持久保存已领取任务与结果 outbox；结果回传丢失时再次回传，而不重新执行。
- 当前网关写作业只领取一次。领取响应丢失后任务可能尚未进入 Agent 本地记录，此时进入待核对状态，不盲目再次下发。
- unknown 作业保持资源锁定；目前没有人工强制解锁 / 核对界面。不得删库或删除收据来制造重试。
- 停止后续步骤不会伪装为撤销已经发生的重启。浏览器断开也不改变已经批准的范围。

不承诺严格 exactly-once 或事务式 compare-and-restart。外部管理员的修改仍可能与后端状态检查竞争；后续增强需要继续明确其实际保证。

## 6. 数据与审计

SQLite 保存设置、会话、主机快照、任务及事件、作业、配对状态和主机身份。任务计划保存目标、期望版本、影响、验证、恢复说明、hash 与期限；当前不是完整配置版本库。

日志限定目标、数量和行长，并过滤常见凭据模式。脱敏属于尽力处理，不能证明任意应用日志不包含秘密；部署者需要选择合适的登记与外部模型数据范围。原始后端错误正文不直接透传。

任务记录可由控制端主机管理员修改，不宣称防篡改。有限采样历史不替代专业时序数据库。数据及私钥默认位于忽略目录 `.local`；备份须使用 SQLite 一致性方式并保护 CA / 签名私钥，Git 不能代替运行数据备份。

## 7. 模型、成本与验证

默认指定 Coding Plan 端点及 `deepseek-v4.1-flash`，不静默切换供应商、模型或消费模式。Provider 实现有限请求 / 工具循环、响应大小与输出约束、超时、取消、参数校验和明确错误；当前供应商失败不会触发备用付费端点。

记录供应商返回的请求次数与 token 用量，不把它们转换成未经核实的套餐额度或金额。凭据只从服务端环境变量或秘密文件读取。

已完成一次真实连通性探测和一次流式只读工具调用冒烟；后者包含 2 次模型请求，使用明确标记的样例资产，不连接真实主机。固定响应测试与实际供应商验证分开记录；详见 [ARK-INTEGRATION.md](ARK-INTEGRATION.md)。当前依赖风险及签名校验路径见 [DEPENDENCIES.md](DEPENDENCIES.md)。

另通过 `scripts/test-linux.mjs` 的隔离 Linux Docker 端到端验收，覆盖 mTLS 注册、发现与日志、审批前无副作用、签名重启、后置验证及重复批准去重。该结果来自真实测试容器，测试资源已清理；不扩展为任意生产服务或完整系统兼容性保证。

## 8. 源码部署与发行边界

已有完整 checkout 且安装 Docker / Compose 的 Linux 主机，可以执行 `sh deploy/install.sh` 从源码构建并启动控制端。该脚本检查依赖与锁文件，不修改现有业务容器，不自动安装 Agent。

安装器引导管理员初始化；可信 CA 分发、主机注册与 helper 白名单仍需按 [RUNNING.md](RUNNING.md) 配置。固定版本公共安装入口见 [DEPLOYMENT.md](DEPLOYMENT.md)。当前没有签名发行包、自动升级、数据库迁移回退或经验证的一键卸载流程。

正式发行前需补齐：平台支持矩阵、独立签名信任、发行清单与完整性校验、兼容性检查、备份恢复演练、关键任务期间升级策略、证书生命周期和失败回退。上述均为后续门槛。

## 9. 后续功能必须保持的约束

以下设计保留用于未来实现，不代表已存在接口或按钮：

- 网站探测只访问已登记目标，并校验重定向、DNS、超时与输出量；防止任意内网 / 元数据访问。
- Compose 更新只开放受管字段；校验解析后配置、环境与覆盖文件等全部依赖，拒绝新增危险权限与挂载。
- 配置审批绑定固化输入，漂移使旧批准失效；秘密可参与私有完整性检查，但不进入可公开差异或 Git。
- 受管配置库与源码库分离；配置恢复是一项新的受控任务。Git revert 不恢复数据卷、数据库或外部副作用。
- 自动化须绑定目标、动作、次数、时间窗与熔断规则，不能让模型自行扩展策略。
- 调整并发、分布式部署或证书信任时，先写明新保证与失效语义，再实现对应协议。
